大模型的上下文（LLM Context）

生成方式：concept-explainer Skill · 领域：大语言模型 / Transformer
上下文窗口Attention生成日期 2026-09-06来源核查 2026-09-06

0概念速览卡

大模型的"上下文"＝模型生成下一段内容时眼前能看到的所有输入（系统提示、用户问题、历史对话、工具返回、检索资料等，全部被切成 token）。它能容纳的上限叫上下文窗口（Context Window）。模型本身没有持久记忆，一次请求结束就"失忆"——上下文就是它唯一的临时工作台。

一句话为什么重要：模型表现好不好，很大程度上取决于你往它的上下文里放了什么、怎么放——这是提示词工程、RAG 和 Agent 设计的共同地基。

1学习目标

  • 能说出"上下文"包含哪几类内容，以及"上下文窗口"的限制来自哪里。
  • 能解释为什么"多轮对话记得住"是一种错觉，以及 Agent 如何靠上下文维持状态。
  • 能说明"窗口很大"≠"都能用好"（知道 Lost in the Middle 现象）。
  • 能针对超长内容给出至少两种上下文管理策略。

2核心问题

  1. 模型推理时到底"看到"了什么？哪些东西占上下文？
  2. 窗口为什么会有限？算力、成本卡在哪？
  3. 为什么说大模型无状态？那"记忆"是怎么来的？
  4. 长上下文里信息放中间为什么容易"丢"？

3我的理解

我把上下文比作模型面前的一张工作台：桌面上能摊开的东西（token）有数量上限——这就是"窗口"；摊不开的旧文件要么扔掉（截断）、要么压成摘要再放上去。模型每一次"下笔"前，都要扫一遍整张桌面来决定写什么，所以桌面上信息的摆放位置和清晰度直接影响它写得好不好。

最容易误解的一点是"记忆"：聊天时模型好像记得我之前说过什么，其实它只是把历史对话原样放回上下文再推理一次。换一个全新会话，它什么都不记得。所以真正能跨会话存在的记忆，必须靠外部存储（数据库、向量库）+ 检索，再读进上下文才生效。

个人补充：读《Lost in the Middle》后我很受触动——模型对长上下文的使用不是"雨露均沾"，而是对开头、结尾更敏感（像人记会议发言的首因/近因效应）。这让我在做提示词和 RAG 时，会特意把最重要的信息放在开头或结尾，而不是随便往中间堆。

4核心机制 / 组成

上下文里有什么（一次请求的典型构成）

底层机制：Transformer 自注意力（Self-Attention）

  • 生成每个新 token 时，模型与窗口内所有已有 token 计算注意力，决定"该参考谁"——这是它能利用长距离信息的根本原因（Vaswani et al., 2017）。
  • 代价：自注意力的时间与内存复杂度随输入长度近似平方增长，窗口因此天然有限；工程上用 KV Cache、FlashAttention 等优化来"省钱"。
  • 模型的 API 是无状态的：每次调用独立；"多轮记忆"是把历史拼进上下文（如上图红色部分）。

窗口用得好不好：Lost in the Middle（迷失在中间）

Liu et al.（2023）实验发现：当相关信息位于长上下文的开头或结尾时，模型表现最好；位于中间时准确率显著下降，呈现 U 型曲线；且上下文越长、中间部分越容易"被忽略"，堆更多检索文档的边际收益很小。

5应用场景（真实具体）

  • 长文档问答：把论文/合同/手册放进上下文直接提问。文档超过窗口时，先分块检索（RAG），只把相关片段放进上下文。
  • RAG（检索增强生成）：检索 → 把 Top-K 结果 + 问题拼进上下文 → 模型基于材料回答。注意：K 不宜过大，相关文档尽量放靠前/靠后位置。
  • Agent 多轮工具调用：上一步工具返回的结果放回上下文，模型"看着结果"决定下一步（与《Agent》资料中的循环呼应）；长任务需要定期把历史"压成摘要"再继续。
  • 会话式应用：客服/学习助手等把多轮历史带入上下文维持"连贯感"，并控制历史长度或做截断策略。

6易混淆与使用边界

易混淆说法澄清
"模型有记忆"模型无状态；记得住是因为历史被放进上下文。关掉会话/超出窗口即"遗忘"。
"上下文窗口越大＝越好用"窗口是"能装多少"；Lost in the Middle 说明"用好多少"是另一回事，中间信息仍易被忽略。
"把整本资料都塞进去最保险"上下文要按 token 计费，还会拖慢推理、稀释注意力；应精选与压缩。
"上下文 = 长期记忆 = 模型学到的东西"都不是。模型"学到的东西"在参数里（训练得到），上下文是请求级的临时输入，两者完全不同。

使用边界

  • 成本与延迟：上下文越长，token 费用与 KV 缓存开销越高；要控制单次请求长度。
  • 关键信息放首尾：依据 U 型曲线，最重要的约束/问题放开头或结尾附近，避免埋在中间。
  • 重锚（Re-anchoring）：长对话中关键状态（订单号、用户要求）应周期性重申，别指望模型"自动一直记得"。
  • 隐私与合规：塞进上下文的数据会随请求发给模型服务方；敏感信息需脱敏、最小化，不要把密钥/隐私写进上下文或提示词文件。

7自测问题

1.（多选）一次大模型请求的上下文可能包含：A. 系统提示 B. 多轮历史对话 C. 工具调用返回 D. 检索到的文档片段
A、B、C、D。它们都会被切成 token 一起参与推理。
2.（判断）大模型具有持久的长期记忆，所以换新会话它仍记得你。
错误。模型无状态；跨会话记忆要靠外部存储+检索，再放回上下文使用。
3.（单选）Transformer 自注意力机制的意义是：A. 让模型记住所有历史会话 B. 让模型生成每个词时可参考窗口内的其他词 C. 替代所有外部存储 D. 压缩视频
B。自注意力让新 token 与窗口内已有 token 交互，是长程利用的基础；复杂度随长度平方增长，也限制了窗口大小。
4.（判断）Lost in the Middle 告诉我们：相关信息放在长上下文中间时，模型往往表现得比放开头/结尾差。
正确。这是 U 型曲线现象（Liu et al., 2023）。
5.（简答）为什么"把 50 篇文档都塞进上下文"常常不如"精选 5 篇放对位置"？
一是成本（token 计费、KV 缓存）上升；二是注意力被稀释、中间信息易丢失，边际收益很小（论文里 20→50 篇只提升约 1.5%）。
6.（简答）Agent 长任务执行到一半，如何防止历史把窗口撑爆？
把已完成的历史压成摘要、丢弃次要细节，或把长内容移到外部存储按需检索，只保留关键状态在上下文（可配合"重锚"）。
7.（单选）"模型参数里学的知识"和"上下文里的信息"的关系是：A. 一样 B. 前者是训练得到的长期知识，后者是请求级的临时输入 C. 上下文会永久改变参数
B。上下文不会修改模型参数（除少数的持续学习/微调场景外，那不是"上下文"的职责）。
8.（简答）给一个你自己的小技巧：如何摆放一次 RAG 问答的上下文？
示例：系统提示与任务目标置前，最相关的 3~5 段材料紧跟其后，问题放最后，并注明"只依据材料回答"；避免把大段无关内容塞中间。（自测开放题，符合原理即可）
