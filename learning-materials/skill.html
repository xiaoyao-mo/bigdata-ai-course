Skill（技能 / 技能包）

生成方式：concept-explainer Skill · 领域：AI Agent 工程 / WorkBuddy
Agent SkillsSKILL.md可复用知识生成日期 2026-09-06来源核查 2026-09-06

0概念速览卡

Skill＝一个文件夹 + 一个 SKILL.md 文件：把"完成某类任务的方法"（适用场景、执行步骤、约束、参考资料、脚本）写成 AI 能读懂、能按需加载的说明书。它把一次次对话里重复出现的"经验"沉淀为可复用、可版本管理、可分享的资产，让通用 AI 快速变成特定领域的"熟手"。

一句话为什么重要：模型的能力像"聪明的应届生"，Skill 像"岗位培训手册"——没有手册，每次任务都要从头教；有了手册，经验可以被沉淀、被复用、被团队共享。本作业的 concept-explainer 就是一个项目级 Skill 的实例。

1学习目标

  • 能说清一个 Skill 的文件结构（SKILL.md、frontmatter、可选脚本与资料）。
  • 能解释"渐进式披露"为什么是 Skill 的核心设计。
  • 能区分 Skill 与提示词、Skill 与 MCP 的边界。
  • 能在 WorkBuddy 里说明项目级（.workbuddy/skills/）与用户级 Skill 的差别，并会"调用"一个 Skill。

2核心问题

  1. Skill 和一段"写得很好的一次性提示词"到底差在哪？
  2. SKILL.md 顶部为什么必须写 name 和 description？
  3. Skill 是怎么"进入"模型的？它和上下文是什么关系？
  4. 什么任务适合沉淀成 Skill？什么情况不适合？

3我的理解

我把 Skill 理解为给 AI 写的"新员工入职手册"：通用大模型什么都略懂一点，但没有"我们这行怎么干活"的具体流程。手册（SKILL.md）把流程写清楚，平时放在书架上（不占桌面空间），接到相关任务时再翻出来照着做——这就是我理解的"按需加载 + 渐进式披露"。

它和普通提示词最大的区别，我概括为三点：结构化（有元数据、有固定章节，能被自动发现与触发）、工程化（放在目录里，可随 Git 版本管理、可被项目共享）、可组合（多个 Skill 可以叠加，模型按需组合使用）。而一次性的提示词用完即弃、难以复用，更谈不上团队共享。

本作业就是一次亲身实践：我（在 AI 协助下）写了 concept-explainer 这个 Skill，再用它生成了本仓库里的概念学习资料——"自己造工具，再用工具干活"，这让我对 Skill 的价值体会很深。

4核心机制 / 组成

一个 Skill 的文件结构（Anthropic 官方定义的标准形态）

concept-explainer/
├── SKILL.md          ← 必须存在；顶部是 YAML frontmatter（name + description）
└── （可选）references/、scripts/ 等子文件，按需加载

SKILL.md 的开头形如：

---
name: concept-explainer
description: 概念学习资料生成器。当用户要求"学习/讲解某个概念"时使用……
---
（正文：适用场景 → 输入要求 → 生成步骤 → 输出结构 → 资料来源与自检要求）

三级"渐进式披露"（Progressive Disclosure）

这正是"Skill 与上下文"的接口：平时只占几十 token 的元数据；触发时才把全文读进上下文——所以装几十上百个 Skill 也不会撑爆上下文窗口。（呼应概念 2。）

Skill 的两种存放层级（以 WorkBuddy 为例）

层级路径特点
用户级 Skill~/.workbuddy/skills/个人所有项目可用
项目级 Skill<仓库>/.workbuddy/skills/随仓库走、团队共享，可用 Git 管理 —— 本作业采用这一级

5应用场景（真实具体）

  • 本作业实例：项目级 Skill concept-explainer 位于 .workbuddy/skills/concept-explainer/SKILL.md，能接收任意新概念（Agent、RAG、Transformer……）自动生成结构化学习资料；本仓库三份概念资料与关系文档均由它产出。
  • Anthropic 官方示例：给 Claude 配 PDF 技能后，它能读取 PDF 并填充表单——SKILL.md 只写"何时用"，表单细节放 forms.md，需要时再读（渐进式披露的典型用法）。
  • 团队/组织场景：把品牌规范、代码规范、报告模板等"程序性知识"沉淀为 Skill 放进仓库，全员共享，随版本迭代。
  • 跨平台：Agent Skills 已成为开放标准（Anthropic 2025-12 发布），同一 Skill 可用于 Claude App、Claude Code、API 等不同环境。

6易混淆与使用边界

易混淆概念区别一句话
Skill vs 提示词提示词是一次性的对话指令；Skill 是结构化、带元数据、可复用可管理的文件资产（"提示词工程化"）。
Skill vs MCPMCP 是连接外部工具/数据的协议（让 AI 能用某个服务）；Skill 是完成任务方法的知识包（教 AI 怎么做）。二者互补：Skill 里的流程可以调用 MCP 工具执行。
Skill vs 普通文件夹/文档Skill 必须遵循约定（SKILL.md + YAML frontmatter），模型才知道何时加载它；乱放的文档不会被自动发现。

使用边界与注意事项

  • 依赖运行环境：Skill 的"自动发现与加载"需要 AI 环境支持（如 WorkBuddy / Claude Code / API 的 Skills 能力）；纯文本对话场景用不了。
  • 会占用上下文：被触发后 SKILL.md 全文进入上下文；写得冗长会浪费 token，应保持精简、按需分层。
  • 安全：Skill 可含可执行脚本，Anthropic 官方提醒"只使用可信来源的 Skill"，避免恶意内容。
  • 需要迭代：Skill 首次编写通常不完美，要通过实际任务测试、修改、再沉淀（这正是本仓库持续迭代的意义）。
  • 不是所有任务都适合：一次性的、变化极大的任务不值得固化成 Skill；适合的是"高频、流程稳定、可复用"的任务。

7自测问题

1.（单选）一个 Skill 目录中，哪个文件是必须存在的？A. README.md B. SKILL.md C. config.json D. main.py
B。SKILL.md 必须存在，且以 YAML frontmatter（name + description）开头。
2.（单选）SKILL.md 顶部的 frontmatter 里，哪两个字段是必需的？A. version 和 author B. name 和 description C. tags 和 date
B。name + description 会在启动时预载入系统提示，用于判断何时触发该 Skill。
3.（判断）Skill 被触发时会把全文一次性塞进上下文；因此装很多 Skill 会立刻撑爆窗口。
错误。平时只载入几十 token 的元数据，只有判断相关时才读全文（渐进式披露），这正是为保护上下文窗口而设计。
4.（单选）MCP 与 Skill 的关系，最准确的说法是：A. 二者完全相同 B. MCP 是连接外部系统的协议，Skill 是任务方法知识包，可互补使用 C. Skill 是 MCP 的旧名字
B。MCP 解决"能不能连上外部能力"，Skill 解决"知不知道怎么做"。
5.（判断）项目级 Skill 放在仓库根目录的 .workbuddy/skills/ 下，可随 Git 版本管理与团队共享。
正确。这就是本作业把它放进仓库的原因（用户级则在 ~/.workbuddy/skills/）。
6.（简答）为什么说 Skill 是"提示词的工程化"？
因为 Skill 把经验写成带元数据、有固定结构、按需加载、可版本管理、可分享的文件，而不是散落在对话里的一次性文本。
7.（判断）Skill 只要写得好，任何环境都能自动触发。
错误。触发依赖 AI 环境对 Skills 的支持（自动扫描/描述匹配）；且模型需具备读文件等能力才能加载内容。
8.（简答）你有一个每周都要做的固定流程任务，值不值得做成 Skill？为什么？
值得。高频、流程稳定、可复用正是 Skill 的最佳场景；做成 Skill 后每次不用重复写要求，还能随实践迭代改进。（开放题，合理即可）
